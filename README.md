# Отчёт по задачам Битрикс24

Веб-приложение формирует отчёт по списанному времени одного сотрудника за
месяц или произвольный период. PHP **8.3**, Symfony **7.4**, PostgreSQL **15**.

## Что учитывается

- Доступные владельцу вебхука задачи, где сотрудник сейчас исполнитель или
  соисполнитель и зарегистрировал время в периоде.
- Период применяется к `CREATED_DATE` записи, обе календарные даты включены.
  Это дата регистрации трудозатрат, не восстановленный календарь работы.
- Складываются `SECONDS`, включая значения меньше минуты и суммы больше суток.
- Роль на момент выборки: исполнитель или соисполнитель. Если сотрудника уже
  убрали из этих ролей, его старые списания не войдут в новый отчёт.
- HTML с деталями записей и CSV с итогами по задачам; результат сохраняется
  до очистки. Кнопка «Собрать заново» создаёт новое задание.
- Даты — `d.m.Y H:i:s`, время — накопленные часы:минуты; точные секунды сохраняются.
  «Компактная версия» показывает ссылки и дробные часы, «Скопировать» — для чата.

## Архитектура

Symfony Security защищает интерфейс одной учётной записью оператора. Формы
используют CSRF, Twig экранирует данные, CSV защищён от формул в текстовых ячейках.
Справочник сотрудников кешируется на 15 минут.

Интерфейс использует официальный UI Kit Битрикс24 2.14, Vue 3.5+ и Vite.
Twig передаёт только данные экрана в HTML-безопасном JSON и сохраняет рабочую
версию без JavaScript. Навигация, вход и формы остаются под управлением Symfony;
SPA-маршрутизатора нет. Подробности: [UI и сборка](docs/bitrix-ui.md).

Форма создаёт задание в PostgreSQL. `app:reports:collect` собирает данные и выходит;
постоянный worker не нужен. По умолчанию мягкий бюджет 45 секунд, прогресс
сохраняется для следующего запуска. Advisory lock защищает от параллельного сбора.
Страница показывает частичные строки и ошибки, обновляя данные без перезагрузки.
Неполные суммы и CSV явно помечены. Подробная схема от формы до БД, все поля таблиц,
повторы, хранение, CSV и очистка: [жизненный цикл отчёта](docs/report-lifecycle.md).

Для списка используется классический `tasks.task.list`: REST 3.0 пока разрешает
фильтрацию только по `id`, а нам нужны роли и активность. Это явное исключение,
не автоматический fallback при ошибке. Записи времени — `task.elapseditem.getlist`,
сотрудники — `user.get`. Роли берутся из списка без отдельного запроса каждой задачи.

Все запросы идут последовательно, с общим локальным ограничением 1 запрос/сек.
`QUERY_LIMIT_EXCEEDED`, сетевые ошибки и HTTP 5xx повторяются с задержкой;
`OPERATION_TIME_LIMIT` приостанавливает сбор до `operating_reset_at` с повторной
проверкой. Таймаут запроса — 55 секунд. Другие интеграции с того же IP могут
использовать общий лимит портала: [официальные лимиты](https://apidocs.bitrix24.ru/limits.html).

Doctrine DBAL выбран вместо ORM для небольших служебных таблиц и явных
транзакций прогресса. SDK не требуется для четырёх используемых REST-методов.
Задачи фильтруются на портале: исполнитель ИЛИ соисполнитель, `ACTIVITY_DATE >=`
начало периода. Верхней границы активности нет: позднее списание за прошлый месяц
не должно потеряться. Период самих записей времени проверяется отдельно.

## Настройка

Требуются PHP 8.3 с `pdo_pgsql`, `curl`, `openssl`, `mbstring`, `intl`, Composer
и PostgreSQL 15. Document root веб-сервера — **только `public/`**, не корень проекта.
Не публикуйте `.ai`, `.env`, `vendor`, `var`; для внешнего доступа нужен HTTPS.

В PowerShell задайте явный PHP, не используйте PHP 8.1 из PATH:

```powershell
$reportPhp = 'D:\OpenServer\modules\PHP-8.3\PHP\php.exe'
& $reportPhp .ai/.tmp/composer.phar install
```

В текущей рабочей копии Composer установлен в `.ai/.tmp`. Для нового окружения
используйте собственный проверенный `composer.phar` с PHP 8.3.

Для интерфейса нужен Node.js 22.12+ в ветке 22 или 24+. Соберите frontend:

```powershell
npm ci
npm run build
```

Vite не загружает серверный `.env`. Сборка создаёт `public/build` с хешированными
JS/CSS; её нужно выполнять после изменения `assets/` и включать в поставку.
Для разработки `npm run dev` пересобирает файлы при изменениях без отдельного сервера.

Создайте локальный `.env` по `.env.example` и заполните:

- `APP_SECRET`: длинное случайное значение; `APP_ENV=prod`, `APP_DEBUG=0`
  для внешнего доступа.
- `REPORT_LOGIN`, `REPORT_PASSWORD_HASH`: логин и хеш пароля оператора.
  Хеш создаётся интерактивно: `& $reportPhp bin/console security:hash-password`.
  Если хеш содержит `$`, заключайте значение в одинарные кавычки в dotenv.
- `B24_PORTAL_URL`: HTTPS-адрес портала без `/rest/...` и без токена.
- `B24_WEBHOOK_USER_ID`, `B24_WEBHOOK_TOKEN`: части входящего вебхука.
- `REPORT_TIMEZONE`: по умолчанию `Asia/Yekaterinburg`.
- `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_SERVER`, `DATABASE_PORT`,
  `DATABASE_NAME`: обязательные параметры PostgreSQL в окружении либо `.env`.
  Приложение не загружает локальные профили доступа агента. Окружение имеет приоритет.

Секреты не коммитить, не передавать в аргументах CLI и не публиковать в логах.
Основная БД и отдельная БД с суффиксом `_test` уже созданы в текущем окружении.
В новом окружении создайте их с тем же владельцем перед миграциями.

```powershell
& $reportPhp bin/console doctrine:migrations:migrate --no-interaction
& $reportPhp bin/console cache:clear
& $reportPhp -S 127.0.0.1:8080 -t public
```

Откройте `http://127.0.0.1:8080`, создайте отчёт и вручную запустите сбор:

```powershell
& $reportPhp bin/console app:reports:collect
```

Без команды задания останутся queued, если не выбрана галочка «Сформировать сразу».
Она после валидации запускает тот же сборщик для нового отчёта, если блокировка
свободна; запрос формы ожидает выполнение. Бюджет 45 секунд мягкий, текущий шаг
может завершиться позже. При выходе по бюджету повторите команду;
`--time-limit=120` переопределяет значение 45. На production запускайте через cron;
OpenServer-планировщик не настраивается. Примеры — в документации жизненного цикла.
После смены вебхука очистите кеш; встроенный PHP-сервер не для production.

Ежедневная очистка завершённых/ошибочных отчётов старше 7 дней (настройте планировщик):

```powershell
& $reportPhp bin/console app:reports:purge
```

## Проверки

Тесты используют **отдельную БД** `DATABASE_NAME_test`, не таблицы основной БД;
HTTP Битрикс24 подменён контролируемыми ответами. Миграции тестовой БД:

```powershell
& $reportPhp bin/console doctrine:migrations:migrate --env=test --no-interaction
& $reportPhp bin/console cache:clear --env=test --no-debug
& $reportPhp vendor/bin/phpunit
& $reportPhp vendor/bin/phpstan analyse --no-progress
& $reportPhp bin/console lint:container
& $reportPhp bin/console lint:yaml config
& $reportPhp bin/console lint:twig templates
npm run build
& $reportPhp vendor/bin/phpunit tests/Controller
npx playwright install chromium
npm run test:ui
```

Браузерные тесты используют синтетические HTML-fixtures из PHPUnit и отдельный
локальный сервер. Фильтр REST проверен на настроенном тестовом портале; это
не заменяет сверку итоговых сумм на боевом облачном портале.
MCP предоставляет документацию, а не доступ к данным портала. Его смешанные
ответы по REST/REST 3.0 сверяются с официальными страницами конкретной версии.

Недоступные/удалённые задачи не восстановить через вебхук. Сбор — не атомарный
снимок портала: новые задачи после верхней границы ID не попадут в текущий запуск,
а изменения времени во время сбора требуют повторного отчёта.

Проектирование: [спецификация](docs/superpowers/specs/2026-10-02-task-time-report-design.md).
Текущие изменения: [выборка и быстрый запуск](docs/superpowers/specs/2026-10-02-report-selection-design.md).
Ход реализации: [план](docs/superpowers/plans/2026-10-02-task-time-report.md).
Результаты и границы проверки: [проверка реализации](docs/verification.md).

На странице отчёта доступен [калькулятор зарплаты](docs/salary-calculator.md):
календарная норма кешируется, расчёт выполняется в браузере и добавляется
в компактный текст. Введённые суммы на сервере не сохраняются.

На главной отчёты можно удалять с подтверждением: AJAX обновляет список
без перезагрузки. Во время работы сборщика удаление временно недоступно.
