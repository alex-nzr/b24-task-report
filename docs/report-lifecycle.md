# Как работает отчёт: от формы до очистки

Эта документация описывает фактическую реализацию после перехода на
`app:reports:collect`. PHP 8.3, Symfony 7.4, PostgreSQL 15; интерфейс Vue +
официальный Bitrix24 UI Kit. Постоянный worker и Messenger для сбора не нужны.

## 1. Общая схема для пользователя

```text
Выбор сотрудника и дат → POST /reports → report_runs (queued)
                                              ↓
ручной запуск / cron → app:reports:collect → REST Битрикс24
                                              ↓
                            report_tasks + report_errors + прогресс report_runs
                                              ↓
страница /reports/{id} ← GET /reports/{id}/progress ← PostgreSQL
                                              ↓
                         GET /reports/{id}/csv → скачивание файла браузером
```

Без галочки форма только заказывает отчёт. «Сформировать сразу» после валидации
вызывает тот же конечный сборщик для нового ID в запросе формы; HTTP-ответ ждёт
его окончания. Обычный ручной/cron-сбор не зависит от открытой вкладки. Быстрый
запуск связан с HTTP-запросом: его остановка/таймаут могут прервать сбор, но
зафиксированные шаги остаются в БД. Само открытие страницы сбор не запускает.

Постоянный worker — «дежурный», ожидающий поручения. Cron — «будильник», который
запускает конечную программу по расписанию. Здесь выбран второй подход: задания
и контрольные точки находятся в БД, команда выполняет доступную работу и выходит.
Это сохраняет возобновление без постоянно открытого терминала. Цена — задержка
до следующего запуска cron; локально нужно самостоятельно запускать команду.

## 2. Вход и выбор параметров

`GET /login` показывает вход оператора. Symfony Security проверяет логин/хеш
пароля из окружения, CSRF, ограничивает попытки и сохраняет сессию. Все маршруты
отчётов, включая JSON-прогресс и CSV, требуют `ROLE_REPORT`. Сейчас это один
оператор, не многопользовательская система с отдельными правами на каждый отчёт.

На `GET /` `ReportController::index()` получает сотрудников через
`EmployeeDirectory::all()`. Справочник кешируется на 900 секунд; при промахе
`BitrixClient::employees()` читает страницы классического `user.get` с фильтром
`USER_TYPE=employee`. Ключ/данные кеша — в файловом пуле `cache.bitrix` под `var/`.
Если справочник недоступен, показывается безопасный код ошибки; новый отчёт не
создаётся. На странице также показаны последние 20 заданий из `report_runs`.

По умолчанию даты — первый день текущего месяца и сегодня в `REPORT_TIMEZONE`.
Выбранный месяц не имеет специальной логики: можно задать любой корректный период.
Форма `ReportRequestType` содержит сотрудника, даты, необязательную галочку и CSRF.

После нажатия «Сформировать отчёт» браузер отправляет обычный `POST /reports`:

- `report_request[employeeId]`: ID выбранного сотрудника;
- `report_request[from]`, `report_request[to]`: даты `YYYY-MM-DD`;
- `report_request[collectNow]=1`: только если выбрано «Сформировать сразу»;
- `report_request[_token]`: токен CSRF `report_create`.

Vue не вызывает вебхук и не рассчитывает трудозатраты. Контроллер проверяет CSRF,
Symfony Form — сотрудника и даты, `ReportPeriod` — календарную корректность и
порядок дат. При ошибке возвращается HTML с HTTP 422, введённые данные и объяснение;
при неверном CSRF — HTTP 403. Задание при этом не создаётся.

Обе даты включены. Внутренний интервал — от 00:00 первого дня до 00:00 дня
**после** последней даты, правая граница исключена. Например, 1–30 сентября
означает `[1 сентября 00:00; 1 октября 00:00)` в часовом поясе отчёта.

Успешная форма вызывает `ReportRepository::create()`: один SQL INSERT создаёт
запись задания с ID из 32 hex-символов, выбранными датами, ID/именем сотрудника и
часовым поясом. Начальный статус `queued`. Никаких сообщений Messenger больше
не отправляется. Если collectNow включён, общий сборщик пытается взять ту же
блокировку, что cron: при занятости сразу оставляет задание queued, при свободной
работает только над новым отчётом с мягким бюджетом 45 секунд. Другие задания
быстрый запуск не обрабатывает. После этого HTTP-ответ перенаправляет браузер
на `GET /reports/{id}`. Полная готовность не гарантирована: оставшееся собирается
следующим ручным/cron-запуском. Shell и постоянный процесс не запускаются.

## 3. Где хранится отчёт: таблицы PostgreSQL

HTML/PDF/CSV-файл в качестве итогового отчёта на сервере не сохраняется.
Источник истины — запись задания и её дочерние строки/ошибки в PostgreSQL.
HTML и CSV строятся из этих данных при чтении. Общая сумма отдельно не хранится:
она вычисляется по сохранённым `seconds`, без повторных запросов в Битрикс24.

### `report_runs`: параметры, состояние и контрольная точка

| Поле | Тип / начальное значение | Назначение |
| --- | --- | --- |
| `id` | varchar(32), PK | Идентификатор отчёта, используется в URL и связях |
| `employee_id` | integer | Чей учёт времени выбирается |
| `employee_name` | text | Имя на момент создания; переименование сотрудника не меняет сохранённое имя |
| `date_from` | date | Первый включённый календарный день |
| `date_to` | date | Последний включённый календарный день |
| `timezone` | varchar(64) | Часовой пояс периода и отображения повторов |
| `status` | varchar(20), `queued` | Состояние задания, см. ниже |
| `cursor_id` | integer, 0 | ID последней окончательно обработанной задачи, включая задачи с ошибкой |
| `max_id` | integer, NULL | Верхняя граница ID, фиксируется при начале обхода |
| `checked_tasks` | integer, 0 | Количество законченных проверок задач, не число строк с трудозатратами |
| `total_tasks` | integer, NULL; >= 0 | Количество задач исходной отфильтрованной выборки; знаменатель прогресса |
| `attempts` | integer, 0 | Бюджет обычных неудач текущего этапа; паузы OPERATION_TIME_LIMIT не расходуют его |
| `retry_at` | bigint, NULL | Unix-время, раньше которого задание нельзя повторять |
| `error_code` | varchar(128), NULL | Безопасный код текущей паузы/глобальной ошибки; история — в report_errors |
| `created_at` | timestamptz, время БД | Создание задания; от него отсчитывается хранение |
| `started_at` | timestamptz, NULL | Зафиксировано начало успешного обхода/верхняя граница |
| `finished_at` | timestamptz, NULL | Завершение либо окончательное прерывание |
| `pending_tasks` | jsonb, `[]` | Необработанный остаток полученной страницы задач |
| `last_processed_at` | timestamptz, NULL | Последний шаг; используется при выборе следующего задания |

Индексы: первичный ключ, `report_runs_created`, `report_runs_ready` по
`status, retry_at, last_processed_at`. Статусы:

| Статус | Что означает |
| --- | --- |
| `queued` | Задание создано, команда ещё не начала обход |
| `running` | Есть прогресс/готовность к следующему шагу; это не гарантия, что сейчас жив PHP-процесс |
| `waiting` | Повтор запрещён до retry_at; нужен текущий или следующий запуск команды |
| `complete` | Обход завершён, нерешённых зарегистрированных ошибок нет |
| `complete_with_errors` | Обход завершён, но есть ошибки; итог неполный |
| `failed` | Нельзя достоверно продолжить общий обход, например не получена страница задач |

Последние три статуса терминальные: команда их повторно не выбирает.
`complete` означает полноту только для доступной вебхуку выборки, а не всего
портала и не недоступных/удалённых задач.

### `report_tasks`: сохранённые строки с известным временем

| Поле | Тип | Назначение |
| --- | --- | --- |
| `run_id` | varchar(32), FK | Связь с report_runs; ON DELETE CASCADE |
| `task_id` | integer | ID задачи Битрикс24 |
| `data` | jsonb | Данные строки и записи времени |

Составной PK `(run_id, task_id)` и UPSERT защищают от удвоения строки при повторе
после прерывания. `data` содержит `id`, `title`, `status` задачи Б24,
`responsibleId`, `role`, `seconds` и `entries`. `entries` — выбранные записи
с ID/TASK_ID/USER_ID/SECONDS/CREATED_DATE/DATE_START/DATE_STOP/COMMENT_TEXT,
если соответствующие поля вернул портал. В браузер передаётся меньший whitelist:
ID, дата, секунды и комментарий записи, без служебных данных.

Если сотрудник не списал время по задаче в периоде, строки здесь нет. Ошибка
получения времени тоже не создаёт «нулевую» строку: неизвестное время — не ноль.
Если время известно, но роль не получена, строка есть с ролью
«Не удалось определить» и отдельной ошибкой в `report_errors`.

### `report_errors`: история ошибок по этапам

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | bigserial, PK | Идентификатор записи ошибки |
| `run_id` | varchar(32), FK | Отчёт; ON DELETE CASCADE |
| `task_id` | integer, NULL | Проблемная задача; NULL при ошибке общего списка |
| `task_title` | text, NULL | Известное название задачи |
| `stage` | varchar(32) | `task_list`, `time_entries` или `participants` |
| `error_code` | varchar(128) | Код API/валидации, без raw-текста ошибки |
| `attempts` | integer | Число неудачных обращений этапа, включая паузы лимита; это диагностический счётчик, не бюджет обычных повторов |
| `state` | varchar(20) | pending/exhausted/resolved |
| `retry_at` | bigint, NULL | Следующий повтор этого этапа, Unix-время |
| `created_at` | timestamptz | Первое сохранение ошибки |
| `updated_at` | timestamptz | Последнее изменение ошибки/разрешение |

Уникальность `NULLS NOT DISTINCT (run_id, task_id, stage)` не допускает множества
дублирующих ошибок одного этапа, включая глобальные с NULL task_id. Повтор
обновляет запись, код и счётчик. Это агрегированная история этапа, не журнал
каждого HTTP-запроса; предыдущие разные коды в одной записи не сохраняются.

`pending` — запланирован повтор; `exhausted` — повторов не будет либо ошибка
неповторяемая; `resolved` — проблемный этап успешно выполнен позже. Исправленные
ошибки остаются видны для диагностики, но не делают полный итог неполным.
Секреты, endpoint вебхука, тела HTTP-ответов и трассировки здесь не хранятся.

### Служебные/исторические таблицы

`doctrine_migration_versions`: `version` — применённая версия миграции,
`executed_at` — когда применена, `execution_time` — длительность в миллисекундах.
Таблицей управляет Doctrine Migrations, это не данные отчёта и purge её не трогает.

`messenger_messages` и её индекс удалены миграцией 004: сборщик их не использует.
Локально перед удалением подтверждено отсутствие сообщений. Обратная миграция
создаёт пустую таблицу, не восстанавливает сообщения или прежние статусы заданий.
Очередь приложения — только report_runs.

## 4. Как работает `app:reports:collect`

Точка входа CLI — `src/Command/ReportCollectCommand.php`, общий цикл — `ReportRunner`;
этот же цикл вызывает контроллер при быстром запуске. Один шаг —
`ReportProcessor::step()`, SQL — `ReportRepository`, REST — `BitrixClient`.

1. Проверяет `--time-limit`: положительное целое число; по умолчанию **45**.
   Неверное значение даёт код выхода 2 без сбора.
2. Берёт PostgreSQL session advisory lock `(240024, 1)`. Если другой сбор держит
   lock, печатает сообщение и выходит с 0, не обрабатывая задания.
3. Выбирает готовый report_runs: queued/running/waiting и retry_at отсутствует
   либо наступил. Приоритет — давно не обрабатывавшееся задание по
   `COALESCE(last_processed_at, created_at)`, далее created_at/id.
4. Выполняет один шаг и снова выбирает задание, пока есть работа и бюджет времени.
5. При изначально пустом списке выходит сразу. Если после выполненных шагов есть
   близкий повтор, который помещается в оставшийся бюджет, коротко ожидает его.
   Если повтор позже бюджета, выходит: дальнейший сбор — в следующем запуске.
6. Освобождает lock в finally. После аварийного завершения процесса PostgreSQL
   освобождает session lock при закрытии соединения; курсор/строки остаются в БД.

**45 секунд — мягкий бюджет, не жёсткое убийство процесса.** Перед новым шагом
время проверяется, но уже начатая задача заканчивается. Один REST-запрос может
занять до 55 секунд; у задачи могут быть несколько страниц времени/запросов.
Поэтому фактическая длительность команды иногда больше time-limit.
Прогресс надо фиксировать согласованно, не прерывать транзакцию посередине.
При запуске из формы также действуют лимиты PHP/веб-сервера и прокси: они могут
закончить HTTP-запрос раньше. Тогда сохранённые шаги продолжаются через CLI/cron;
быстрый запуск не заменяет планировщик и не гарантирует готовность за один запрос.

Вывод команды: ID отчёта, статус, число проверенных задач, текущий безопасный код
ошибки и итоговое число шагов. Один шаг может быть завершением обхода, не только
задачей. Код 0 означает, что команда отработала штатно, **не** отсутствие ошибок
в данных: проверяйте статус и report_errors. Непредвиденный сбой команды даёт 1
и `COLLECTION_COMMAND_FAILED` без трассировки. Если недоступна БД, она физически
не может записать эту ошибку в таблицу: необходимо также контролировать CLI-вывод.

## 5. Один шаг сбора и обращения к Б24

При первом шаге классический `tasks.task.list` получает страницу ID DESC с
фильтром `DOER = сотрудник` (исполнитель или соисполнитель) и
`ACTIVITY_DATE >= начало периода`. Наибольший ID сохраняется в max_id, top-level
total — в total_tasks. Пустая выборка даёт max_id=0 и total_tasks=0.
Следующие страницы читаются ID ASC по 50 с теми же фильтрами и
`ID > cursor_id`, `ID <= max_id`. Остаток страницы сохраняется в pending_tasks.

REST 3.0 сохраняет общий приоритет, но список — осознанное исключение: в его
TaskDto только id имеет Filterable, роль и activity доступны не для фильтрации.
Вложенный OR с ACCOMPLICE не используется: его INNER JOIN исключает задачи без
соисполнителей до проверки роли исполнителя. DOER поддерживается ядром, но пока
не описан в официальной таблице параметров; проверен прямым REST-запросом.
Классический обработчик умеет DOER и дату на уровне SQL; конкретный синтаксис
проверен на настроенном тестовом портале. Это уменьшает страницы задач и запросы их времени,
но не гарантирует мгновенную обработку 10 000 активных подходящих задач.

Верхней границы активности нет: октябрьская активность не исключает задачу
со списанием за сентябрь. Нижняя граница опирается на обновление активности при
обычном ручном списании; нестандартные импорты/изменения исторических данных могут
требовать отдельной сверки. Роли текущие: снятые соисполнители, наблюдатели и
администраторы без нужной роли исключены даже при наличии времени.
Новые ID выше max_id появятся только при новом отчёте.

Для первой задачи страницы `TaskReportCollector::collectTask()`:

1. Читает классический `task.elapseditem.getlist` с task ID, USER_ID сотрудника,
   `>=CREATED_DATE=start` и `<CREATED_DATE=end`, сортировкой ID ASC и страницами 50.
   При полной странице читает следующую; проверяет, что пагинация продвигается.
2. `ReportCalculator::summarize()` проверяет ID, абсолютные ISO-даты со смещением,
   целые неотрицательные секунды и принадлежность задачи. Дополнительно фильтрует
   сотрудника/период, исключает дубли `(TASK_ID, ID)` и складывает **SECONDS**.
   MINUTES не используется: 23 секунды не округляются до нуля.
3. Если выбранных записей нет, строки трудозатрат не будет. Если есть — сохраняются
   их детали и сумма. CREATED_DATE означает дату регистрации записи времени,
   не реконструированный календарь фактической работы по DATE_START/DATE_STOP.
4. Роль новых задач определяется из responsibleId и accomplices списка:
   исполнитель либо соисполнитель. Дополнительного запроса участников нет.
   Поле общего времени задачи не используется для суммы.
5. В одной короткой DB-транзакции UPSERT сохраняет строку, разрешает исправленные
   ошибки и обновляет остаток страницы, cursor_id, checked_tasks. Длительный HTTP
   не выполняется внутри этой транзакции. Задача без списаний тоже двигает курсор.
6. Когда следующая страница пуста, ставится complete либо complete_with_errors
   по наличию нерешённых ошибок, заполняется finished_at.

Роли/состояния — текущие на момент полученных данных, не исторические. Это не
атомарный снимок портала: данные могут измениться между запросами. Повторную
сверку после изменений выполняйте новым отчётом.

## 6. Ошибки, повторы и сохранение известного времени

Общий лимитер — последовательные запросы, до одного в секунду. HTTP 429/5xx,
QUERY_LIMIT_EXCEEDED и сетевые ошибки повторяемы. Бюджет — пять обычных неудач
этапа: после первой/второй/третьей/четвёртой — задержки минимум 2/4/8/16 секунд;
пятая завершает повторы. retry_at может быть позже согласно ответу API.

OPERATION_TIME_LIMIT ждёт operating_reset_at, если он получен, иначе используется
безопасная пауза с повторной проверкой. Такие ожидания не расходуют обычный бюджет,
но отражаются в диагностическом счётчике report_errors.attempts. Другие интеграции
с того же IP/портала тоже могут влиять на лимиты.

- Ошибка времени: сохранить task ID/название, stage=time_entries, код и состояние.
  Не писать фиктивный ноль. При окончательной ошибке перейти к следующей задаче.
- Историческая ошибка роли: сохранить уже известное время и роль «Не удалось определить»,
  stage=participants. При повторе запросить **только участников для сохранённой
  строки**, не перечитывать успешно полученное время. Ошибка resolved только после
  успешного получения/проверки роли; сумма не удваивается.
- Ошибка списка: task_id=NULL, stage=task_list. Пока повтор возможен — waiting;
  после исчерпания/неповторяемой ошибки — failed, поскольку неизвестны остальные
  задачи. Уже сохранённые строки и сумма остаются доступны.

Ранее REST 3.0 связанных участников возвращал HTTP 500 на рабочей задаче.
Новая выборка берёт участников из списка, поэтому этот дополнительный запрос
для новых отчётов не нужен. Старые ошибки/строки сохраняются для диагностики.

Официальные источники: [лимиты](https://apidocs.bitrix24.ru/limits.html),
[поля REST 3.0](https://apidocs.bitrix24.ru/api-reference/tasks/fields-rest-v3.html).
MCP повторно проверен и доступен. Его ответ по списку смешивает REST 3.0 и старые
параметры; контракт сверялся с отдельной страницей версии, ядром и REST тестового портала.

## 7. Что видит браузер и где итог

`GET /reports/{id}` читает report_runs, report_tasks, report_errors и суммирует
seconds. Показываются строки при любом статусе, даже failed. Если статус не
complete, сумма явно неполная. Ошибки показаны с этапом, кодом, попытками,
состоянием и временем следующего повтора в часовом поясе отчёта.

Прогресс — checked_tasks из total_tasks, причём total фиксируется на старте.
Это не неизменяемый снимок портала: при смене ролей/активности число может измениться.
У старых отчётов знаменатель NULL, показывается только число обработанных задач.
Даты записей — d.m.Y H:i:s в timezone отчёта. Время — накопленные HH:mm, часы
не обнуляются после суток. Секунды не округляются при суммировании; их часть
меньше минуты скрывается только при отображении (23 секунды отображаются 00:00).

«Компактная версия» открывает B24-попап: ссылки используют employee_id отчёта,
а не ID текущего исполнителя. Каждая строка — HTTPS-ссылка и часы с суффиксом ч,
в конце итог. Дробные часы округлены до четырёх знаков, лишние нули убраны.
Для любого статуса кроме complete в текст входит предупреждение о неполноте.
«Скопировать» использует Clipboard API; если браузер запретил доступ/нет HTTPS,
текст выделяется для ручного копирования. Без JS доступен раскрываемый текст.

Начальные данные передаются в JSON с HTML-safe кодированием. Vue обновляет их
через авторизованный `GET /reports/{id}/progress` каждые пять секунд без
перезагрузки страницы; следующий запрос планируется после завершения предыдущего.
Endpoint возвращает whitelist `{run, rows, errors, total, complete}` с
private/no-cache/no-store. `complete` здесь означает терминальное состояние,
а не гарантию полноты — смотрите run.status. Никакого вызова Б24 при polling нет.

На терминальном статусе запросы прекращаются; при уходе со страницы таймер и
текущий fetch отменяются. При сетевой ошибке уже видимые данные сохраняются и
показывается предупреждение. Детали строк не закрываются на каждом обновлении.
Без JS доступен серверный HTML; актуальный прогресс тогда обновляется вручную.

Итоговый отчёт — те же сохранённые строки/ошибки с терминальным статусом.
Он не подтягивает изменения портала автоматически. «Собрать заново» отправляет
защищённый CSRF `POST /reports/{id}/refresh` и создаёт **новый** ID с теми же
сотрудником/датами/часовым поясом; предыдущий результат не перезаписывается.

## 8. CSV: что это, куда сохраняется и когда удаляется

CSV — текстовый табличный формат, открываемый Excel/LibreOffice. Не XLSX, не PDF.
`GET /reports/{id}/csv` собирает текущий сохранённый снимок без REST-запросов,
даже если сбор ещё идёт или завершился с ошибкой.

Сначала записываются статус/предупреждение полноты, сотрудник, период и часовой
пояс. Далее колонки: ID, задача, статус Б24, исполнитель ID, роль, время ч:м,
секунды, число записей. Затем сумма и секция всех ошибок (включая resolved):
ID/название задачи, этап, код, попытки, состояние, Unix-время следующего повтора.
UTF-8 с BOM, разделитель `;`, текст в кавычках при необходимости. Потенциальные
формулы в динамических текстовых ячейках нейтрализуются префиксом апострофа.

`CsvExporter` использует временный поток php://temp, читает готовую строку и
закрывает поток. PHP может использовать временное хранилище для большого потока,
но приложение **не создаёт постоянного файла в public/var**. Ответ HTTP имеет
Content-Disposition с `report-{id}.csv`; браузер скачивает файл туда, куда
настроено сохранение загрузок, либо спрашивает папку. Заголовок Cache-Control —
private/no-store. Последующие скачивания формируются заново из БД.

Скачанный файл — независимая копия на компьютере пользователя: приложение его
не обновляет и не удаляет. После удаления отчёта из БД новый CSV по его URL
получить нельзя (404), но ранее скачанная копия остаётся у пользователя.

## 9. Очистка `app:reports:purge`

На главной можно удалить отдельный отчёт сразу: POST `/reports/{id}/delete`
с CSRF-токеном `delete_{id}`. Vue просит подтверждение, отправляет AJAX и получает
обновлённые последние 20 отчётов; строки плавно появляются/исчезают без reload.
При ошибке строка остаётся, выводится пояснение; повтор после уже выполненного
удаления безопасен. Без JS доступна обычная POST-форма с redirect на главную.
Удаление использует общий advisory lock со сборщиком: при занятой команде — 409
без удаления. Удаляются задание, строки и ошибки каскадом, без корзины.
CSV не хранится на сервере; уже скачанные копии у пользователя не удаляются.

`ReportMaintenanceCommand` вызывает `ReportRepository::purgeExpired()`.
Удаляются только complete/complete_with_errors/failed, у которых created_at
раньше текущего времени БД минус семь дней. Это срок **от создания**, не от
finished_at. Долгий сбор, завершённый спустя семь дней, подходит для ближайшей
очистки. queued/running/waiting не удаляются автоматически, даже если старые.

DELETE report_runs каскадно удаляет report_tasks и report_errors. Команда печатает
число удалённых заданий, не сумму дочерних записей. `Удалено отчётов: 0` — нормальный
результат. Она не собирает отчёты, не запускает cron, не чистит браузерные файлы,
UI-сборку, кеш сотрудников или таблицу миграций.
Удаление из БД не имеет корзины: восстановление возможно из внешней резервной
копии, либо новый сбор создаёт другой отчёт с текущими данными портала.

## 10. Ручной запуск и production cron

Локально планировщик не настроен и не нужен. Из корня проекта:

```powershell
$reportPhp = 'D:\OpenServer\modules\PHP-8.3\PHP\php.exe'
& $reportPhp bin/console app:reports:collect
# По умолчанию 45; можно задать другой мягкий бюджет:
& $reportPhp bin/console app:reports:collect --time-limit=120
# Очистка — отдельная операция:
& $reportPhp bin/console app:reports:purge
```

После достижения бюджета ещё не завершённые задания продолжаются следующей
командой. Долгая пауза API тоже требует последующего запуска. Завершённые/failed
задания не возобновляются этой командой: для них используйте «Собрать заново».
Старый отчёт, уже failed до перехода, автоматически не перезапускается.

Пример Linux cron (пути/пользователя/лог замените своими; не устанавливается
приложением). PHP CLI обязан быть 8.3 с теми же расширениями/доступами:

```cron
* * * * * cd /srv/b24-task-report && /usr/bin/php8.3 bin/console app:reports:collect --env=prod --no-debug >> /var/log/b24-task-report-collect.log 2>&1
15 3 * * * cd /srv/b24-task-report && /usr/bin/php8.3 bin/console app:reports:purge --env=prod --no-debug >> /var/log/b24-task-report-purge.log 2>&1
```

Процессу нужны права на var/cache/var/log и DB-доступ. Настройте ротацию и
контроль кода выхода/логов. Более долгий запуск защищён advisory lock от наложения
со следующим cron. Не запускайте одновременно старый worker: он остановлен
штатным сигналом при переходе, пакеты Messenger удалены.

После обновления кода: `composer install`, миграции, очистка Symfony cache,
`npm ci`/`npm run build`. Миграция 004 добавляет total_tasks и удаляет старую очередь.
Незавершённые старые отчёты переводятся в failed с SELECTION_CHANGED, сохраняя
строки/ошибки: так не смешиваются старые правила отбора с новыми. Для них нажмите
«Собрать заново». На другом сервере требуется `doctrine:migrations:migrate --no-interaction`.

## 11. Секреты и ограничения

`config/bootstrap.php` загружает настройки только в серверный процесс. Реальное
окружение имеет приоритет над обычными dotenv-файлами. DB-параметры должны быть
заданы явно. Никакие локальные профили доступа агента приложение не загружает.
В браузер/CSV/логи не передаются пароль БД, хеш оператора, токен вебхука, APP_SECRET.
Vite не читает backend dotenv: envDir=false. Public document root — только public.
Никакие секреты не нужны в аргументах CLI или cron.

Доступ определяется владельцем вебхука. Ошибку известной задачи мы покажем,
но задачи, которые REST вообще не вернул из-за прав/удаления, перечислить нельзя.
Не сравнивайте checked_tasks с количеством строк: проверенные задачи могут
не иметь времени выбранного сотрудника в периоде. Для полной приёмки сверяйте
несколько реальных задач/дат/ролей с порталом; автоматические тесты используют
изолированную тестовую БД и синтетические HTTP-ответы.
