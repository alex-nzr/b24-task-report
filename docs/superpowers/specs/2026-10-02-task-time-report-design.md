# Отчёт по задачам и времени сотрудника

Статус: решение принято запросом пользователя на реализацию; приложение реализуется по отдельному плану.
Дата: 2026-10-02. Этот документ сохраняет проектные решения; актуальные инструкции запуска и ограничения находятся в README.md. Развёртывание не выполняется.

## Подтверждённые требования

- Один облачный портал Битрикс24; обращения через входящий вебхук, параметры в `.env`.
- Отчёт по одному сотруднику за месяц или произвольный период.
- Учёт облачных лимитов и использование официального MCP при разработке.
- Стек выбирается по задаче; Symfony предпочтителен, но не обязателен.
- PHP строго ветки 8.3; PostgreSQL 15. Параметры окружения: `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_SERVER`, `DATABASE_PORT`, `DATABASE_NAME`.
- В отчёт входят все доступные задачи, где сотрудник списал время за период, независимо от роли.
- Показывать роль сотрудника: исполнитель, соисполнитель, наблюдатель или без роли.
- При наличии одноимённого метода в классическом REST и REST 3.0 использовать REST 3.0.
- README не более 200 строк; комментарии и docstring только при практической пользе.
- Работа непосредственно в текущем репозитории, без новых веток и worktree.

## Варианты решения

1. **Рекомендуется: Symfony, веб-интерфейс, фоновый сбор.** Выбор сотрудника и дат, просмотр результата, CSV; длительная выгрузка не удерживает браузерный запрос. Требуется отдельный процесс worker.
2. **Консольная команда с CSV.** Меньше компонентов и проще запуск; неудобна для сотрудника, которому нужен интерфейс. Подходит, если отчёт формирует только технический оператор.
3. **Постоянная синхронизация задач и времени в БД.** Быстрые повторные отчёты, но сложнее исправления, удаления и повторная синхронизация. Для первой версии объём и частота использования не оправдывают этот подход.

## Предлагаемый состав первой версии

- PHP 8.3, Symfony 7.4 LTS, Twig, HttpClient, Validator, Security.
- PostgreSQL 15 через Doctrine DBAL: состояния отчётов и очередь Symfony Messenger с Doctrine transport. ORM не требуется для этих небольших служебных таблиц.
- Один worker, один активный сбор на портал. Использовать `pdo_pgsql`, доступный в локальном PHP.
- HTML-отчёт и CSV из одного сохранённого результата; PDF и XLSX не входят в предлагаемую первую версию.
- PHPUnit и PHPStan с конфигурацией по фактически установленным зависимостям.
- Прямые REST-запросы через HttpClient. SDK пока не нужен для выбранного небольшого набора методов; это решение можно пересмотреть при расширении интеграции.

PHP проверен: `D:\OpenServer\modules\PHP-8.3\PHP\php.exe`, версия 8.3.6; доступны curl, openssl, PDO, pdo_pgsql, mbstring, intl. В Composer ограничить PHP диапазоном `>=8.3 <8.4`.
Symfony 7.4 требует PHP не ниже 8.2: https://symfony.com/releases/7.4.

## Предлагаемая семантика отчёта

Подтверждено: включать все доступные задачи, где сотрудник записал время в выбранном периоде, независимо от ответственного, роли и текущего статуса задачи. Задачи без такого времени не включать.

- Сотрудник определяется по `USER_ID` записи времени, а не по текущему `RESPONSIBLE_ID` задачи.
- Фильтр периода применяется к `CREATED_DATE` записи времени. Это учёт зарегистрированных трудозатрат, а не восстановление фактического календаря работы.
- Запись относится целиком к периоду по этому полю. Не разделять её длительность между днями или месяцами; для такого разделения требуется отдельное бизнес-правило.
- Даты интерфейса включают обе границы. Внутренний интервал: начало первого дня включительно, начало дня после последнего дня исключительно.
- Часовой пояс задаётся `REPORT_TIMEZONE`; предварительно предлагается `Asia/Yekaterinburg`. API получает даты с явным смещением, приложение сравнивает моменты времени после нормализации.
- Суммировать целые `SECONDS`; не складывать дополнительно `MINUTES`. Итог форматировать как часы, минуты и секунды, в том числе более 24 часов.
- Завершённые и старые задачи учитываются. Дата создания или завершения задачи не определяет дату учтённого времени.
- Выводить текущие название, ответственного и статус задачи; историческое состояние этих полей не восстанавливается.
- Роль определяется на момент сбора: `responsible.id` совпадает с сотрудником — исполнитель; иначе его ID в `accomplices` — соисполнитель; иначе в `auditors` — наблюдатель; иначе — без роли. При пересечении ролей действует этот порядок. «Без роли» не означает автоматически администратора; постановщик без перечисленных ролей также попадает в эту категорию.
- Если сведения о ролях не удалось получить, не присваивать «без роли»: задание не завершать успешно до устранения ошибки.
- Не добавлять время подзадач в родителя: каждая запись относится только к своему `TASK_ID`.

В документации `CREATED_DATE` описано неоднозначно: таблица называет его датой создания, а примечание о ручном внесении прошлой работы — датой начала. До приёмки проверить на тестовых примерах ручную запись за прошлую дату и запись таймером. Не обещать точное распределение фактической работы без этой проверки.

## Сценарий пользователя

Предложение: приложение для одного авторизованного оператора, которому разрешено смотреть данные в пределах прав вебхука. В первой версии нет многопользовательского разграничения по сотрудникам.

1. Оператор входит, выбирает сотрудника, начальную и конечную даты; быстрый выбор месяца заполняет эти даты.
2. Приложение валидирует параметры и создаёт задание; браузер получает страницу состояния.
3. Worker собирает данные; интерфейс показывает число проверенных задач и состояние: очередь, сбор, ожидание лимита, готово или ошибка.
4. Готовый отчёт показывает сотрудника, период, часовой пояс, время формирования, ограничения видимости, задачи и общий итог.
5. Для каждой задачи: ID, название, ссылка, текущий статус, ответственный, роль сотрудника, время сотрудника, число записей. Раскрытие строки показывает даты, длительности и комментарии записей.
6. CSV содержит те же задачи и итоги; подробные записи доступны в HTML.
7. Повторное открытие использует сохранённый результат. Кнопка обновления запускает новый сбор и не выдаёт старый результат за актуальный.

## Проверенные методы и выбор версии REST

Приоритет REST 3.0: endpoints `/rest/api/{userId}/{webhookToken}/{method}` для методов, доступных в новой версии. Для методов без аналога REST 3.0 использовать `/rest/{userId}/{webhookToken}/{method}`. Версия выбирается явно для каждого метода, а не по форме случайного ответа или ошибки. Не переходить на старый REST при ошибке прав или лимита.

| Метод | Назначение | Контракт |
| --- | --- | --- |
| `user.get` | Справочник сотрудников | Классический REST, пока не найден документированный аналог REST 3.0; постранично по `next`, сохранять только ID и имя. |
| `tasks.task.list` | Задачи, доступные вебхуку | REST 3.0: `order`, массив `filter`, `select`, `pagination`; ответ `result.items`. Не использовать `start` или `next`. |
| `tasks.task.get` | Участники и роль сотрудника | REST 3.0: `id`, `select` со связанными полями `responsible.id`, `accomplices.id`, `auditors.id`; только для задач с подходящими записями времени. |
| `task.elapseditem.getlist` | Записи времени по задаче | Классический REST: аналога REST 3.0 в проверенной документации не найдено. Позиционные `taskId`, `order`, `filter`, `select`, `params`; массив `result`, поля UPPER_CASE. |
| `batch` | Возможная оптимизация независимых запросов | При группировке методов REST 3.0 — batch REST 3.0; для классического метода времени — классический batch только после проверки позиционного контракта. Версии не смешивать в пакете. |

Для списка задач REST 3.0 выбирать `id`, `title`, `responsibleId`, `status`, `groupId`, `activity`. Поле суммарного времени задачи не использовать для месячного итога.
Начальный размер страницы — 50; `pagination.limit`, фильтр по `id` и сортировка `id ASC` обеспечивают последовательное перечисление. Сведения о связанных участниках брать через `tasks.task.get`, а не ожидать их в списке задач.

Для записей времени выбирать `ID`, `TASK_ID`, `USER_ID`, `SECONDS`, `CREATED_DATE`, `DATE_START`, `DATE_STOP`, `COMMENT_TEXT`.
Фильтр: `USER_ID`, `>=CREATED_DATE`, `<CREATED_DATE`; сортировка `ID asc`; `params.NAV_PARAMS.nPageSize=50`, `iNumPage` начиная с 1.

## Алгоритм сбора и полнота

1. Проверить настройки, доступ к выбранному сотруднику и работоспособность чтения задач.
2. Зафиксировать верхний ID доступной задачи; перечислять задачи по ID по возрастанию с ограничением этим ID. Не ограничивать выборку текущим ответственным, ролью, статусом или датой изменения.
3. Для каждой задачи загрузить все страницы записей времени сотрудника в интервале. При полной странице запрашивать следующую; завершить после неполной или пустой страницы. Не применять `start` к этому методу.
4. Проверять типы, пользователя, принадлежность задаче и границы периода также на стороне приложения. Повторяющиеся ID записей учитывать один раз в рамках задачи.
5. При отсутствии подходящих записей не добавлять задачу в результат. Для включаемой задачи получить участников через REST 3.0 и определить роль. При ошибке чтения не трактовать её как нулевое время или отсутствие роли.
6. Сохранять промежуточное состояние после каждой обработанной задачи. При повторном чтении текущей задачи заменять её результат целиком, чтобы не удвоить сумму.
7. Публиковать итог только после полного прохода. Незавершённый сбор или потеря доступа дают состояние ошибки с описанием неполноты, а не успешный отчёт.

Гарантия ограничена данными, видимыми владельцу вебхука. Недоступные или удалённые задачи восстановить нельзя. Разрешения обычного сотрудника могут быть недостаточны для отчёта по всему подразделению.
REST не даёт атомарного снимка: изменения во время сбора могут повлиять на результат. Сохранять время начала и окончания сбора; обновление запускает новое чтение. Верхний ID стабилизирует перечень новых задач, но не замораживает их записи времени.

Цена первой выгрузки: страницы списка задач плюс как минимум один запрос времени на каждую доступную задачу. При 1000 задачах и скорости 1 HTTP-запрос/с это порядка 17 минут только на чтение времени, без дополнительных страниц и пауз. Это расчёт, не гарантия времени выполнения.

Пакеты для позиционного метода времени вводить только после проверки их сериализации на тестовом портале. Не предполагать, что именованные параметры или `taskId=0` дают корректную глобальную выборку.

Оптимизация по последней активности: поле `activity` есть и доступно для сортировки, но страница REST 3.0 `tasks.task.list` документирует фильтрацию только по `id`. Не использовать недокументированный серверный фильтр `activity` и не исключать задачи по нему локально, пока не подтверждено обновление этого поля при любом способе списания времени. Возможный будущий безопасный фильтр — только нижняя граница периода: верхняя граница потеряет задачи с последующей активностью. Основной критерий включения всегда записи времени сотрудника.

## Лимиты и сбои

- Начальная скорость — 1 HTTP-запрос/с, последовательное выполнение; лимитер общий для всех заданий этого приложения на портал.
- Облачные устойчивые скорости по документации: 2 запроса/с для прочих тарифов и 5 для Enterprise; не считать лимит полностью свободным, если другие приложения используют тот же исходящий IP.
- Один облачный запрос ограничен 60 секундами; клиентский предел — 55 секунд.
- `QUERY_LIMIT_EXCEEDED`: повтор с растущей задержкой и jitter; не запускать параллельную серию.
- `OPERATION_TIME_LIMIT`: сохранить прогресс, отложить продолжение до `operating_reset_at` с запасом; при повторной блокировке ждать следующего сброса.
- Проверять `time.operating` и `operating_reset_at`. Не фиксировать 480 секунд как гарантированный лимит облака: в актуальной статье это пример, значение задаётся конфигурацией Битрикс24.
- Если batch будет включён, не более 50 команд; начать с небольших пакетов. Вложенные вызовы сохраняют собственный учёт ресурсоёмкости.
- Сетевые таймауты и временные 5xx повторять до 5 раз. Ошибки прав, токена и параметров не повторять автоматически.
- Для длительной блокировки использовать отложенное сообщение Messenger; worker не должен удерживать транзакцию или спать до сброса лимита.

| `ReportRepository` | Состояния задания, курсор и сохранённые строки через DBAL. |
| `GenerateReportHandler` | Обработка фонового сообщения, продолжение и отложенные повторы. |
| Контроллеры, Forms и Twig | Ввод, авторизация, состояние, HTML и экспорт готового отчёта. |

Хранить `report_runs` с параметрами, состоянием, курсором, временами сбора и безопасным кодом ошибки; `report_tasks` с нормализованными строками, ролью сотрудника и их записями времени. Очередь хранится в служебной таблице Messenger. Все таблицы в PostgreSQL 15; структура управляется миграциями.
Создание отсутствующей базы и применение миграций — отдельный шаг реализации. Сначала проверить версию сервера, существование целевой базы и права пользователя; существующие базы и роли не изменять. Использовать доступы из профиля `prod` без вывода значений.
Локальные результаты удалять через 7 дней; справочник пользователей кэшировать на 15 минут. Записи времени не использовать как постоянное зеркало Битрикс24. Автоматический повтор продолжает то же задание, явное обновление создаёт новое.

## Безопасность и конфигурация

- `.env` с реальными параметрами исключён из Git; `.env.example` содержит только имена и безопасные placeholders.
- Предлагаемые параметры приложения: `B24_PORTAL_URL`, `B24_WEBHOOK_USER_ID`, `B24_WEBHOOK_TOKEN`, `REPORT_TIMEZONE`, `REPORT_LOGIN`, `REPORT_PASSWORD_HASH`, `MESSENGER_TRANSPORT_DSN`.
- Подключение DBAL настраивать отдельными `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_SERVER`, `DATABASE_PORT`, `DATABASE_NAME`, `driver=pdo_pgsql`, `server_version=15`; не дублировать пароль в генерируемом `DATABASE_URL`. Для реализации брать ровно эти пять значений через `.ai/tools/get-secret.py prod <KEY>` в переменные процесса. В приложении использовать переменные окружения; профиль доступов не публиковать и не коммитить.
- Вход через Symfony Security с одним настроенным оператором; CSRF для запуска и обновления. Просмотр, состояние и экспорт требуют авторизации.
- Выбранный сотрудник задаёт содержание отчёта, но не является механизмом авторизации. Любой допущенный оператор получает доступ в пределах прав вебхука.
- Адрес портала задаётся только серверной конфигурацией, HTTPS, без перенаправлений на другой host. Пользователь не передаёт произвольный URL или REST-метод.
- Токен находится в пути REST URL: отключить запись полного URL, тел запросов и необработанных исключений HttpClient в логи, profiler и диагностику.
- HTML экранируется Twig; комментарии рассматриваются как текст. CSV защищён от формул для ячеек, начинающихся с `=`, `+`, `-`, `@`.
- Приложение только читает портал; методы добавления и изменения данных не используются.
- Проверки реального портала проводят позднее с разрешённым доступом к секретам через переменную процесса; на этом этапе секреты не читались.

## Проверки перед реализацией и приёмкой

- Состав задач подтверждён. Предложенные настройки для первой версии: веб-интерфейс, HTML/CSV, один оператор, часовой пояс `Asia/Yekaterinburg`; объём влияет на длительность сбора, но не меняет состав данных.
- Контрактные проверки: REST 3.0 списка задач, фильтра по ID и связанных участников; классический позиционный payload времени, `NAV_PARAMS`, ручная запись за прошлую дату и необходимые права вебхука.
- Проверить PostgreSQL 15, создание отсутствующей целевой БД и миграции; интеграционные тесты БД выполнять на отдельной тестовой базе, не на данных профиля prod.
- Unit: границы дней/месяцев, смещения времени, 23 секунды при `MINUTES=0`, сумма свыше 24 часов, дубли, чужой `USER_ID`, подзадачи.
- Unit для роли: четыре значения, пересечение ролей, смена исполнителя и списание времени без участия в задаче; роль не влияет на включение или сумму.
- Integration с HttpClient mock: несколько страниц задач и времени, 50 записей плюс следующая страница, временные ошибки, лимиты, возобновление и отсутствие удвоения.
- Functional: вход, CSRF, валидация дат, изоляция вебхука от браузера, состояние задания, совпадение сумм HTML и CSV, защита CSV от формул.
- Приёмка: сверить ручной расчёт нескольких задач за конкретный месяц с результатом приложения; проверить задачу со временем нескольких пользователей и работу на задаче с другим ответственным.

## Источники и обнаруженные неточности

MCP `b24-dev-mcp` использован по протоколу Streamable HTTP: `tools/list`, `bitrix-search`, `bitrix-method-details`, `bitrix-article-details`.
Сервер предоставляет документацию, а не данные рабочего портала. Обращений к самому порталу не было.

- В ответах MCP для `tasks.task.list`, `tasks.task.get` и `batch` смешаны параметры и ответы классического REST и REST 3.0. Сверять URL и контракт на странице конкретной версии, не генерировать запрос из смешанного ответа.
- `bitrix-article-details` с названием «Лимиты REST API» фактически вернул «Особенности списочных методов». Проверять заголовок и URL результата; лимиты получены с указанной в AGENTS.md страницы.
- Для `task.elapseditem.getlist` MCP не перечислил `TASK_ID` в фильтрах, хотя официальная страница его содержит. Первая версия не зависит от этого фильтра.
